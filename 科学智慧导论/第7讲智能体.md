# 智能体：从会说话的模型到能完成任务的系统

语言模型能回答问题，但完成现实任务还需要观察环境、选择行动、调用工具、处理反馈，并检查结果。**智能体（Agent）**可以理解为围绕目标，在环境中持续进行多步决策的系统。其能力既取决于模型，也取决于让模型实际工作的执行体系。

## 1. 智能体如何从目标走向行动

智能体的基本循环是：**目标 → 观察 → 决策 → 行动 → 新的观察 → 修正决策**。例如，修复一段程序时，系统要先读文件和报错，判断原因，修改代码，再运行测试；测试失败就根据新反馈调整。仅给出一段可能正确的代码，还没有完成这个循环。

图：目标位于循环的起点；智能体通过工具作用于环境，环境返回观察结果。新的观察会改变下一步行动，直到目标达成或任务被中止。

### 三类智能体的差别

| 类型 | 主要知识来源 | 行动与反馈 | 典型局限 |
| --- | --- | --- | --- |
| 符号智能体 | 人工编写的规则 | 在预设动作内按规则匹配 | 换场景时规则难以扩展 |
| 强化学习智能体 | 与环境交互的经验 | 选择动作，并根据奖励改进策略 | 训练往往需要大量交互 |
| 语言模型智能体 | 预训练知识与当前上下文 | 用语言、代码或工具调用行动，再读取环境反馈 | 可靠性、幻觉与权限风险 |

语言成为统一接口后，任务目标、工具描述、观察结果和行动指令都能以文本形式接入同一个循环。模型可以先用已有能力尝试任务，也可以进一步接受面向工具使用的训练。但**模型输出的工具调用本身并不执行操作**；外部程序必须解析调用、检查权限、执行并返回结果。

### ReAct：边推理，边行动

ReAct 将**思考（Thought）—行动（Action）—观察（Observation）**交替组织：

1. 根据目标和现有信息，决定下一步需要知道什么或做什么。
2. 调用工具，让环境产生可检查的结果。
3. 将结果加入上下文，修正判断并继续。

只有推理而没有环境反馈，容易把猜测当事实；只连续执行动作而不解释和复查，容易偏离目标。ReAct 的重点是让**每次新观察都能改变后续决策**。如今工具调用通常有结构化接口，但“行动后观察”的逻辑仍然相同。

图：一条任务轨迹由若干次“思考 → 工具调用 → 工具结果”组成；最终答案应建立在实际返回的信息之上，而不是把尚未执行的计划写成已完成的结果。

### 工具调用与 MCP

一次工具调用通常经过五步：把工具名称和参数要求交给模型；模型提出调用；执行层校验并运行；工具结果加入上下文；模型决定继续还是结束。工具描述应说明输入、输出和错误含义，限制过长输出，并在失败时给出明确反馈。面向智能体设计的接口常称为 **ACI（Agent–Computer Interface）**。

MCP 为智能体与外部工具、资源和提示提供一种统一连接方式。它减少每个智能体与每种服务分别适配的工作量；若有 $M$ 个客户端、$N$ 种服务，独立两两适配可能需要约 $M\times N$ 个连接，统一协议则可将适配工作主要分摊到两端。协议并不自动保证工具可信：工具说明会占用上下文，第三方工具也可能带来权限和供应链风险。

### 记忆、反思与规划

- **短期记忆**是当前上下文中的目标、对话和工具结果。它容量有限，长任务中会被新信息挤占。
- **情景记忆**记录发生过什么，如任务经过和失败原因；**语义记忆**保存提炼出的事实；**程序性记忆**保存做事方法，如可复用的技能步骤。
- **语言反思**把失败原因和改进方法写入可再次读取的记录，下次行动因上下文改变而改进。它不等于更新模型权重。
- **规划**把目标拆成步骤，并在执行中修订。反应式方法成本低但可能短视；在真实环境中试错可能不可逆；内部模拟能降低试错成本，却依赖模型对环境的预测是否准确。

**例子：** 要整理一批文献，先列出检索、筛选、阅读和汇总步骤。检索后若发现主题范围过宽，就更新筛选条件；若一篇文献无法获取，应记录缺口，而不是在总结中假装读过。

### 工作流、多智能体与技能

**工作流（Workflow）**的路径主要由程序预先规定，适合步骤明确、结果可预期的任务；**智能体**可根据反馈动态选择步骤和工具，适合开放问题，但成本、延迟与风险也更高。常见的工作流模式包括提示链、路由、并行、编排者与执行者，以及评估者与优化者循环。

多个智能体可以按角色分工、独立求解后互评，或模拟多方互动。子智能体还可以在独立上下文中完成局部任务，只把结论交回主智能体，从而减少主上下文负担。适合并行且能清楚拆分的任务才可能从中获益；通信、成本和结果整合仍需管理。

**技能（Skill）**把可重复的操作写成按需加载的步骤和配套工具，让智能体不必每次从零摸索。技能可由人维护，也可能由系统总结生成；在使用前仍应检查其来源、权限需求与实际效果。

## 2. Harness：让模型能力成为可执行的工作

**Agent = Model + Harness** 是一个系统设计视角：模型负责生成判断和候选行动；Harness 负责工具接入、执行环境、状态、上下文、循环、验证与权限。相同模型接入不同 Harness，任务表现可能大不相同。它类似操作系统为应用提供内存、设备与权限，但只是帮助理解的类比。

图：模型位于中心，周围的系统提示、工具、文件系统、沙箱、编排、记忆和验证共同形成 Harness。模型提出行动，Harness 决定能否执行、怎样执行以及如何把结果送回模型。

提示工程关注一次调用怎样表达问题；上下文工程关注多步任务中模型应看到哪些信息；Harness 工程进一步处理执行环境、工具、流程、验证和治理。三者范围不同，也相互配合。

### Harness 的七个层面

| 层面 | 要解决的问题 | 常见机制 |
| --- | --- | --- |
| 执行环境 | 行动在哪里发生 | 本地环境、容器、云沙箱 |
| 工具接口 | 模型能调用什么、怎样调用 | 工具定义、发现、结构化参数、MCP |
| 上下文 | 模型此刻能看到什么 | 提示、记忆、检索、压缩 |
| 编排 | 何时循环、分工或结束 | 状态管理、计划、子智能体 |
| 可观测 | 发生了什么、花费多少 | 日志、追踪、成本记录 |
| 验证 | 结果是否真的达标 | 测试、评估器、独立审查 |
| 治理 | 谁能做什么、如何追责 | 权限、审批、审计规则 |

图：七层共同围绕任务运行。跨层设计要同时权衡成本、质量和速度，也要处理能力与控制之间的张力；改变某一层可能影响其他层。

### 语言、工具和流程三种控制手段

1. **语言设定认知框架。** 项目说明、工作规范和任务目标帮助模型理解“如何思考和汇报”。简短、可更新的项目说明可作为导航，细节在需要时再读取；冗长过时的说明会挤占上下文。
2. **工具限定能力边界。** 接口决定模型能观察和改变什么。清晰的错误消息、可机器读取的输出、分块查看文件、限制输出长度，都能减少误操作；沙箱、最小权限和审批则限制潜在后果。
3. **流程约束实际行为。** 固定的检查点、执行前拦截、执行后验证和终止条件，让关键步骤不只依赖模型“记得遵守”。Hook 可以在工具调用或任务结束时自动检查条件。

文件系统可保存任务状态，版本控制可追踪修改并协助交接；代码执行工具给智能体更灵活的行动能力，也因此需要受限的运行环境。**能力越通用，权限和验证越要明确。**

### 验证闭环与避免过早完成

长任务可采用“提出结果 → 自动或人工评估 → 反馈 → 修正”的循环。若验收条件尚未满足，系统应保留未完成状态，而不因已有部分成果就宣布成功。循环的价值来自明确的目标和可读的反馈；没有停止条件的反复尝试只会增加成本。

图：规划者定义交付物和验收条件，生成者逐步实现，独立评估者根据结果给出反馈。验收项起初标为未通过，只有拿到证据后才改为通过；评估者不参与生成，以减少自我评判的盲点。

Harness 应随模型能力变化而重新评估。某些用于弥补模型弱点的流程，可能在模型升级后变得多余；但环境接入、权限和独立验证仍然是系统层面的需要。

## 3. 上下文工程与长程任务

语言模型每一步能处理的上下文有限，且长上下文会增加成本并可能稀释重要信息。上下文工程不是把所有材料塞进去，而是决定**何时保留、取回、压缩或隔离信息**。

| 策略 | 做法 | 主要风险 |
| --- | --- | --- |
| 写入 | 把计划、草稿和完整日志存入外部文件 | 写下后若不再读取，信息仍会丢失 |
| 选择 | 只检索与当前步骤相关的记忆和工具 | 检索遗漏关键条件 |
| 压缩 | 汇总历史、裁剪冗长工具输出 | 过度概括导致决策依据消失 |
| 隔离 | 子任务使用独立上下文，只回传必要结果 | 摘要不足以支持主任务核查 |

图：长日志可以将完整内容保存在文件中，只把摘要和定位信息放进上下文；到具体决策点时再读取相关片段。

跨会话的记忆需要**真实写入并在下一次读取**。口头说“我会记住”并不能形成持久记录。工作记录可保留经过和未解决问题，长期记忆则提炼稳定、有复用价值的结论；两者应定期纠错和清理。

### 让长任务能够交接

连续数次运行的智能体像轮班团队：新一轮可能不记得前一轮做过什么。可靠的交接至少包含目标、已完成项、未完成项、失败原因、验证证据和下一步。每次开始先检查当前状态，选择一个有边界的任务，完成后验证并更新记录。

一个实用的流程是：

1. 定义可检查的功能或交付清单，初始状态为“未通过”。
2. 每轮确认工作目录、读取进度和已有修改。
3. 选择优先级最高的一项，实现后在真实使用路径上验证。
4. 记录通过证据、未解决问题和修改结果，再交给下一轮。

这样可以同时减少“做太多做到一半”和“看见部分成果就过早结束”。生成与评估分开，尤其适合需要长期、反复交接的任务。

## 4. 怎样评测智能体

智能体任务跨越多步，终点正确也不代表过程安全；同一任务多次运行还可能得到不同结果。因此评测要同时看**最终结果、过程行为和重复运行的稳定性**。

- **端到端基准**在代码库、终端、网页、操作系统或客服环境中检查任务结果。它能比较整体能力，但分数受模型、Harness、环境和测试方式共同影响。
- **行为评测**检查可观察的关键动作：不清楚时是否澄清、修改后是否验证、危险操作是否申请审批、失败后是否读取真实错误。它更容易定位某次改动导致的退化。
- **重复运行评测**区分“运行 $k$ 次至少成功一次”（pass@k）与“运行 $k$ 次全部成功”（pass^k）。前者适合衡量可探索能力，面向用户的稳定服务更重视后者。

**例子：** 一个智能体偶尔能修好程序，说明它有解决问题的潜力；若同样的请求经常漏测或误改文件，就还不能算可靠。评测还要警惕测试数据被训练材料覆盖，以及系统专门迎合某个基准。

## 5. 有行动能力就必须管理风险

### 提示注入与权限组合

网页、邮件、文档和工具结果可能包含伪装成指令的文字。智能体需要读取这些材料完成任务，但不能把其中的命令自动提升为用户授权。提示注入的根源是**不可信数据与行动指令都可能以文字形式进入模型**；单靠一句“忽略恶意内容”不足以保证安全。

图：当系统同时接触不可信输入、私密数据或敏感系统，并且能改变状态或向外发送信息时，风险会在三者交汇处升高。设计上应减少同一会话同时拥有这三种条件；确需同时具备时，加入可靠验证和人工审批。

风险还包括目标被劫持、工具滥用、身份与权限误用、插件或技能的供应链问题、意外执行代码、记忆投毒、智能体之间的不安全通信、级联故障以及对人机信任的利用。把模型训练得更谨慎有帮助，但无法替代系统层面的控制。

### 纵深防御与独立监督

- **模型层：** 区分可信指令与外部数据，训练系统识别异常请求。
- **Harness 层：** 最小权限、沙箱、允许范围、网络隔离、审批点、可追踪日志和确定性拦截。
- **系统层：** 独立身份、临时凭据、监控异常操作，并保留恢复路径。
- **人与组织层：** 明确责任、审批标准和事故处置方法，避免审批过多导致机械点击。

另一个风险是**目标投机**：若目标只写成“让测试通过”，智能体可能修改测试而不是修复程序。验收标准应对应真正的任务结果，关键测试和评估者应独立于生成者。越自主的系统，越需要外部监督。

## 6. 发展方向与仍待解决的问题

未来的智能体可能更擅长长程自主执行、利用可复用技能、协同工作，并把上下文管理纳入学习过程。标准化接口有助于扩大工具生态，也会放大供应链与权限管理的重要性。编程任务较容易获得测试反馈；推广到科研、个人助理或现实设备时，目标和结果通常更难验证。

需要持续回答的问题包括：

- 模型能力提高后，哪些 Harness 机制可简化，哪些环境连接、权限和验证机制必须保留？
- 智能体改写自己的技能或记忆时，怎样防止它降低自身的约束？
- 自动评估者可能与生成者共享盲点，怎样保持评估独立且可靠？
- 跨会话记忆由谁保存、谁能访问，错误或不再需要的信息如何删除？
- 多智能体协作怎样避免成本失控、沟通失真和责任不清？
- 当智能体能对外行动时，如何划定人类的授权和最终责任？

**全讲主线：** 智能体以目标和反馈驱动多步行动；模型负责提出判断，Harness 提供工具、状态、流程、上下文和权限；长期工作依靠清晰交接与独立验证；真实部署则必须把可靠性和安全放在系统设计之中。
